# Release v4.0.0 — Notification Platform V1

> Part of the Notification Platform program (WP-N1 … WP-N6).
> Companion to `CHANGELOG.md`; the CHANGELOG remains the canonical per-version list.

## Overview

admin-core's in-app notifications now run on a **first-party Notification Platform** instead of Laravel's
notification runtime. One canonical pipeline — `NotificationPlatform::send() → Dispatcher → channel driver(s) → the
notifications store` — replaces `$user->notify(...)`/`DatabaseNotification`, and the `illuminate/notifications`
dependency is gone. Realtime returns as an **optional, off-by-default broadcast channel**.

- **Type:** Major
- **Breaking:** Yes
- **SemVer:** MAJOR — a removed composer dependency, a changed public API (`AdminNotification`), and a store schema
  change (a table-recreating migration).

## Why this release exists

Notifications were a thin layer over Laravel Notifications (`AdminNotification extends Notification`,
`DatabaseNotification`, a uuid-PK `notifications` table). That coupled admin-core to a runtime it did not control and
kept notifications off the package's hybrid-identity standard (ADR-0007). WP-N1 … WP-N6 built and cut over to an
owned platform — *mechanism, not policy* (ADR-0010 … ADR-0014): the kernel orchestrates delivery and never learns
what a notification means.

## Technical changes

- **Platform kernel:** `NotificationPlatform` facade → `PendingNotification` builder → transport-agnostic
  `Dispatcher` → `NotificationChannelManager` (an open, config-seeded + `extend()` registry) → `NotificationChannel`
  drivers. Collaborators: `RecipientResolver`, `ChannelRouter`, `NotificationTypeRegistry`. Frozen public contracts:
  `NotificationMessage`, `OutboundNotification`, `Recipient`, `NotificationChannel`, `DeliveryResult`.
- **Store:** a first-party hybrid table — `bigint id` + public `uuid` + `guard` — via `Models\Notification`
  (`HasPublicUuid`). A package migration performs a **create-or-recreate** of `notifications` on `php artisan
  migrate`.
- **In-app:** `InAppChannel` persists to the store; the Notification Center controller, `/admin/notifications`
  views, and `<x-admin-core::notifications-bell>` read it, scoped by the recipient's morph identity (portal/guard
  aware). `readAll`/`destroy` operate on model instances so cache-invalidation events fire.
- **Optional realtime (`broadcast` channel):** a peer `NotificationChannel`, **off by default** (`NullPublisher`).
  Enable via `notifications.broadcast.enabled` + a driver; add `'broadcast'` to `notifications.default_channels`
  (or `->channel('inapp','broadcast')` per send). Publishes **after** the DB transaction commits, best-effort, on
  each recipient's **owner-only private channel** (one injective morph-identity name shared by publish and auth).
  Fresh `echo.js`/`realtime.js` stubs subscribe the bell and re-sync from the store on connect/reconnect; an additive
  `notifications.unread` JSON endpoint backs the re-sync. See ADR-0014.
- **Config:** new block `notifications.{default_channels, broadcast.{enabled, driver, connection, event,
  channel_prefix}}`.
- **Producers:** both first-party producers (approval requests, generated-resource approver alerts) send through the
  platform.

## Breaking changes

1. **`AdminNotification` is a platform message, not a Laravel `Notification`.** It implements `NotificationMessage`
   and no longer has `via()` / `toArray()` / the `broadcast:` argument. Send with
   `NotificationPlatform::send(new AdminNotification(..., message: '…'), $user)` instead of
   `$user->notify(new AdminNotification(...))` (`message` → the stored `body`).
2. **`illuminate/notifications` removed** from `composer.json`. Hosts that relied on it transitively must require it
   themselves.
3. **Store schema changed** to the hybrid identity; `DatabaseNotification` is gone. The migration **recreates** the
   `notifications` table and does **not** migrate existing rows.
4. **Old realtime path removed** (`ADMIN_CORE_REALTIME` + its Laravel-broadcast stubs). Realtime is now the new
   opt-in broadcast channel (a fresh implementation).

## Migration

| You have… | Do this |
|---|---|
| A fresh install | **Nothing** — the package migration creates the store on `php artisan migrate`. |
| Producers calling `$user->notify(new AdminNotification(...))` | Switch to `NotificationPlatform::send(new AdminNotification(..., message: '…'), $user)`. |
| A pre-v4.0.0 Laravel `notifications` table with rows | **Back it up and drop it** before upgrading (the migration recreates the table; rows are **not** migrated), then `php artisan migrate`. |
| The old `ADMIN_CORE_REALTIME` realtime | Remove it. To keep realtime, opt into the broadcast channel (below); otherwise delete the old published `resources/js/echo.js` + `resources/js/realtime.js`. |
| A wish for realtime (optional) | Set `ADMIN_CORE_BROADCAST=true` + `ADMIN_CORE_BROADCAST_DRIVER=reverb`, add `'broadcast'` to `notifications.default_channels`, configure a Laravel broadcasting connection, and re-publish stubs with `admin-core:install --access --force`. |
| The vestigial `Notifiable` trait on `User` | Harmless; remove it if nothing in your own app uses it. |

## Compatibility

- **Default behavior is unchanged for existing sends** other than the `AdminNotification` call-site: routing defaults
  to `['inapp']` and broadcast binds a `NullPublisher`, so no realtime traffic occurs until you opt in.
- Public contracts are frozen (ADR-0013); a custom `NotificationChannel` written against them keeps working.

## Quality gates

- **1,095 tests / 4,350 assertions; PHPStan (larastan) L5 clean; 58 Vitest tests.** The broadcast channel adds
  unit + integration + architecture tests (the architecture test pins the kernel as transport-agnostic). A
  four-dimension adversarial review with per-finding verification confirmed and fixed three findings before release.
