## Overview

`Support\Search` now generates portable LIKE SQL on every supported database — SQLite, MySQL/MariaDB,
PostgreSQL~~, and SQL Server~~. Previously it emitted SQLite/MySQL-only constructs and worked only on SQLite,
the sole engine the CI suite exercised.

- **Type:** Patch
- **Breaking:** No
- **SemVer:** PATCH — bug fix only; results are identical under default collations.

## Why this release exists

The Naming / View Configuration program was discovered by dogfooding an enterprise LMS on PostgreSQL. Before the
naming defect could be reproduced and fixed, a more fundamental portability defect had to be closed: `Support\Search`
hand-rolled raw LIKE SQL that broke on every non-SQLite engine. Because every search surface shares this SQL — the
DataTable relation/list-filter search, the Select2 foreign-key dropdown, the media-library search, the global-search
omnibox, and the API list search — all of them 500-ed off SQLite. This release makes search portable so the rest of
the program could be verified cross-database.

## Technical changes

- Identifiers are quoted by the connection's query grammar (`$grammar->wrap()`), never a hardcoded backtick.
- JSON (translatable) search renders the driver's own accessor — `json_extract`/`json_unquote` (MySQL/SQLite),
  `->>` (PostgreSQL)~~, `json_value` (SQL Server)~~ — instead of a hardcoded `json_extract()`.
- The LIKE escape sentinel changed from `\` to `!` (one constant, applied by both the pattern builder and the
  `ESCAPE` clause), so the clause is a valid string literal on MySQL/MariaDB under default `sql_mode`.
- Matching is consistently case-insensitive via `LOWER()` on both sides — restoring case-insensitive search on
  PostgreSQL (whose `LIKE` is case-sensitive) and matching the DataTable's native search and MySQL/SQLite defaults.
- New CI job `search-portability` runs the Search suite against real PostgreSQL and MySQL (the full suite still runs
  on SQLite), plus per-grammar SQL compile tests.

## Breaking changes

None. No public API, method signature, generated code, or caller changed — the fix is entirely inside
`src/Support/Search.php`.

## Migration

None required.

## Upgrade notes

`composer update`. No configuration, schema, or code changes on the consumer side. PostgreSQL~~/SQL Server~~ search that
previously errored will now work.

## Testing summary

- `tests/TestCase.php` made environment-aware (real driver via `DB_CONNECTION`/`DB_*`, default SQLite in-memory).
- Cross-database CI matrix (PostgreSQL 16, MySQL 8) added.
