# Release v3.0.3 — ErrorLogTest portability fix

> A follow-up PATCH. **Not part of the RFC-0009 Rev 2 program** (v2.86.1–v3.0.0) — a pre-existing test-portability
> fix. Supersedes the incomplete v3.0.1 fix. Companion to `CHANGELOG.md`.

## Overview

Makes the pre-existing `ErrorLogTest` case `it('stores an ARGUMENT-FREE stack trace …')` pass deterministically on
every PHP build, including the GitHub Actions `setup-php` runner — the one that has failed `Test - PHP 8.3` and
`Test - PHP 8.4` on every push since the test was introduced.

- **Type:** Patch
- **Breaking:** No
- **SemVer:** PATCH — test portability only; no runtime behavior change.

## Why this release exists

The test proves that `ErrorLog::capture()` stores an **argument-free** stack trace — a password/token/OTP passed up
the call chain must never be persisted into the admin-viewable `error_logs` table. Its *precondition* (a sanity guard
that the secret really is present, so the arg-dropping is genuinely exercised) asserted on `Throwable::getTraceAsString()`
— the formatted **string** trace.

Two independent INI facts on the GitHub Actions runner defeat that string-based precondition:

1. `zend.exception_ignore_args = On` (php.ini-production / `setup-php` default) — arguments are stripped from traces
   at throw time.
2. `zend.exception_string_param_max_len = 0` (`setup-php` default) — `getTraceAsString()` renders **every** string
   argument as `'...'`, so the raw value never appears in the *string* form **regardless of (1)**.

Because of (2), no INI change can make `getTraceAsString()` contain the secret on that build; the precondition was
un-satisfiable there. The v3.0.1 fix (`ini_set('zend.exception_ignore_args', 0)`) addressed only (1) — argument
*capture* — not the string-rendering cap, so the test kept failing on CI.

## Exact PHP behavior (verified on the `ondrej`/`setup-php` build)

`ErrorLog::capture()` builds the stored trace from the **structured** frames via `ErrorLog::argFreeTrace()`, which
iterates `Throwable::getTrace()` and reads only `file` / `line` / `class` / `type` / `function` — it never reads
`args` and never calls `getTraceAsString()`. The security guarantee is therefore structural.

Reproduced on `ubuntu:24.04` + `ppa:ondrej/php` (the exact source `setup-php` installs), PHP 8.3.32 and 8.4.23, with
`zend.exception_ignore_args=On`, `zend.exception_string_param_max_len=0`:

- `getTraceAsString()` renders the arg as `boom('...')` — the secret is **absent** from the string form (the CI
  failure).
- After a runtime `ini_set('zend.exception_ignore_args', '0')` before the throw, the **structured**
  `getTrace()[0]['args']` is `["SEKRETPASS"]` — the secret **is** present in the frames the feature consumes.

## Technical changes

- `tests/Feature/ErrorLogTest.php` — the sanity precondition now asserts the secret is present in the **structured**
  `Throwable::getTrace()` frames (`collect($e->getTrace())->flatMap(fn ($frame) => $frame['args'] ?? [])`) — the exact
  surface `ErrorLog::capture()` reads — instead of the formatted `getTraceAsString()` string. The runtime
  `ini_set('zend.exception_ignore_args', '0')` that restores those structured args (and its `finally` restore) is
  kept; the stored-trace security assertions are unchanged.

## Why this fix is preferable

- **Preserves the exact test and every assertion.** Nothing is skipped, removed, or weakened; the precondition is
  moved to the correct (and more precise) surface — the one the production code actually consumes.
- **No production change.** No `src/`, config, helper, generator, descriptor, or public-API change — the `ErrorLog`
  production code is byte-identical. The feature was always correct; only the test asserted on the wrong surface.
- **Deterministic everywhere.** `getTrace()` structured args are restored by the runtime `ini_set` on every build,
  so the precondition holds on both the dev default (`ignore_args=Off`, `max_len=15`) and the `setup-php` runner
  (`ignore_args=On`, `max_len=0`).
